B-001 Critical NULL Pointer: shipment_tracking in marketplace-tracking.js Backend Unfixed ▶
Datei: services/marketplace-tracking.js
Risiko: Crash bei Tracking-Push
pushTrackingToMarketplace() greift direkt auf order.shipment_tracking zu, ohne null-Check. Bei Bestellungen ohne Tracking (storniert, ausstehend) → TypeError: "Cannot read property of undefined".
// Line ~95: carrierCode = KAUFLAND_CARRIER_MAP[order.shipment_tracking.carrier] // ^ Crash wenn shipment_tracking null/undefined
Fix: Guard: if (!order?.shipment_tracking?.carrier) return; // skip push
B-002 Critical Race Condition: Stock-Release vs. Marketplace-Sync Backend Unfixed ▶
Datei: services/sync-event-bus.js
Risiko: Overselling, Bestandsfehler
stock:changed Event feuert sync:reserve-stock-release und sofort danach Marketplace-Sync. Wenn Marketplace-Sync den Order-Status auf "completed" setzt bevor Stock-Release bestätigt → Order completed MIT reserviertem Bestand (double-booked).
Fix: Stock-Release atomar innerhalb derselben Transaktion wie Order-Status-Update machen.
B-003 Critical eBay API Fehler werden still ignoriert (HTTP 200 + Errors) Integration Unfixed ▶
Datei: services/order-intake-ebay.js
Risiko: Verlorene Bestellungen
syncEbayOrders() prüft nicht das Errors-Feld in der eBay Trading API Response. eBay kann HTTP 200 mit Error-Liste zurückgeben. Fehlgeschlagene Syncs erscheinen als erfolgreich — Bestellungen bleiben bei eBay, kommen aber nie in die DB.
// Line ~65: const orders = response.OrderArray || []; // Fehlt: if (response.Errors?.length) throw new Error(...)
Fix: Check: if (response.Errors?.length) throw new Error('eBay sync errors: ' + JSON.stringify(response.Errors))
B-004 Critical eBay Status "NotPaid" nicht im OMS-Mapping Integration Unfixed ▶
Datei: services/order-intake-ebay.js
Risiko: Unsichtbare Bestellungen
mapEbayStatus() hat keinen Handler für den eBay-Status "NotPaid". Ergebnis: order.status wird undefined → Bestellung ist im OMS unsichtbar, kann nicht bearbeitet werden.
Fix: Neuen Case: case 'NotPaid': return 'pending'; // oder 'on_hold'
B-005 Critical Bestand wird bei Stornierung NICHT freigegeben Backend Unfixed ▶
Datei: services/order-state-machine.js
Risiko: Inventar-Deadlock, Overselling
Wenn transitionOrder() zu "cancelled" übergeht, wird der reservierte Bestand NICHT freigegeben. Stornierte Bestellungen blockieren Inventar permanent.
// Line ~450: if (newStatus === 'cancelled') { // ... trigger marketplace cancellation ... // // FEHLT: releaseStockReservation(order.products, order.id) // }
Fix: await releaseStockReservation(order.products, order.id) VOR der Marketplace-Stornierung aufrufen.
B-006 Critical NULL Pointer: order.customer.address in shipping-engine.js Backend Unfixed ▶
Datei: services/shipping-engine.js
Risiko: Versand blockiert
shipOrder() → createParcel() greift auf order.customer.address.street1 zu ohne null-Guard. Wenn customer null → TypeError, Bestellung bleibt im Status "packed" hängen.
Fix: Guard: if (!order?.customer?.address) throw new AppError('SHIPPING_ADDRESS_MISSING', 400)
B-007 Critical Dual-Status-Feld: status vs. omsStatus nicht konsolidiert Frontend Unfixed ▶
Datei: OrdersView.tsx, types.ts
Risiko: Falsche Status-Anzeige
Order-Typ hat sowohl status (5 Werte: 'new'|'picking'|'picked'|'packed'|'other') als auch omsStatus (12-State-Model). Frontend nutzt überall: (o as any).omsStatus || o.status. Das "as any" zeigt: Backend liefert inkonsistent — manche Endpoints nur status, andere omsStatus.
const statusKey = (o as any).omsStatus || o.status; // ^ "as any" = Type-System ist kaputt, kein Vertrag zwischen Backend/Frontend
Fix: Backend konsolidieren: ein einziges status-Feld mit 12-State-Enum. Frontend-Type anpassen.
B-008 Critical Versand-Tabs: Unbekannte Status-Werte verschwinden Frontend Unfixed ▶
Datei: components/orders/ShippingView.tsx
Risiko: Unsichtbare Sendungen
ShippingView hat 4 Status-Tabs (ausstehend, in_zustellung, zugestellt, problem). Backend liefert aber auch SendCloud-Roh-Status ('Ready to send', 'In transit', etc.). Sendungen mit nicht-gemapptem Status werden in keinem Tab angezeigt → verschwinden komplett.
Fix: Normalisierungs-Layer in api/client.ts der ALLE Status-Varianten auf kanonische Werte mappt. Fallback-Tab "Sonstige" hinzufügen.
B-009 Critical SevDesk-Export ist nur ein Stub (nicht implementiert) Backend Known ▶
Datei: services/invoice-engine.js
Risiko: Keine automatische Buchhaltung
exportToSevDesk() existiert als Funktion, loggt aber nur "TODO: SevDesk export not yet implemented" und gibt null zurück. Rechnungen werden nie automatisch an SevDesk übertragen.
Fix: Vollständige SevDesk API-Integration implementieren (Kontakt anlegen, Rechnung erstellen, PDF anhängen).
B-010 High SendCloud: Kein Retry bei API-Fehlern Integration Unfixed ▶
Datei: services/shipping-engine.js
Risiko: Versand blockiert bei transientem Fehler
createParcel() ruft SendCloud API genau einmal auf. Bei Timeout oder transienten Fehlern → Bestellung bleibt ohne Label stecken, kein automatischer Retry.
Fix: Retry mit exponential Backoff implementieren (3 Versuche, 1s/3s/9s). Siehe kaufland-api.js als Referenz.
B-011 High Tracking-Push Retry erst nach 24h Integration Unfixed ▶
Datei: services/marketplace-tracking.js
Risiko: 24h Tracking-Verzögerung
ensureMarketplaceTrackingPushed() Safety-Net retried nur Pushes die >24h alt sind. Bei frischem Failure → keine automatische Wiederholung. Kaufland 500 → Tracking kommt erst am nächsten Tag.
Fix: Sofortiges Retry-Event bei Failure emittieren (z.B. nach 5 min), nicht erst nach 24h.
B-012 High Kaufland Webhook-Signatur wird nicht validiert Integration Unfixed ▶
Datei: routes/orders.js (Webhook-Endpoint)
Risiko: Webhook-Spoofing möglich
Eingehende Kaufland-Webhooks werden nicht gegen HMAC-SHA256 Signatur geprüft. Ein Angreifer könnte gefälschte Webhooks senden (Bestellungen stornieren, Tracking ändern).
Fix: HMAC-Signatur-Validierung als Middleware vor dem Webhook-Handler.
B-013 High Kaufland "closed" Status falsch gemappt → "completed" Integration Unfixed ▶
Datei: services/order-intake-kaufland.js
Risiko: Nicht geliefert aber "abgeschlossen"
Kaufland Status 'closed' (Account geschlossen, NICHT Bestellung erfüllt) wird auf OMS 'completed' gemappt. Ergebnis: Geschlossene Accounts werden als erfolgreich zugestellt angezeigt.
Fix: Mappen auf 'cancelled' statt 'completed'. Ggf. Sonderstatus 'account_closed' einführen.
B-014 High Kaufland Einzelpreise gehen verloren Integration Unfixed ▶
Datei: services/order-intake-kaufland.js
Risiko: Falsche Finanzberichte
mapKauflandOrder() extrahiert nur Gesamt-Bestellwert, nicht die einzelnen Unit-Preise. Line Items haben Preis = 0 wenn Quelle Kaufland ist. Rechnungen zeigen €0 pro Position.
Fix: Unit Price aus Kaufland Response extrahieren: item.price / 100 (Kaufland speichert in Cent).
B-015 High Stale Data: Keine Refetch nach Status-Mutation Frontend Unfixed ▶
Datei: OrdersView, ReturnsView, InvoicesView, ShippingView
Risiko: User sieht falschen Status
Nach jeder Mutation (Status-Transition, Refund, Mark-as-Paid, Label-Erstellung) wird die Liste NICHT neu geladen. User sieht alten Status bis zur nächsten manuellen Aktualisierung. Betroffene Stellen: bulkTransitionOrders(), processReturn(), markInvoicePaid(), bulkCreateLabels().
Fix: refetch() nach jeder erfolgreichen Mutation aufrufen. Oder: Optimistic Updates mit React Query.
B-016 High Invoice: amountNet/amountNetto Dual-Feldnamen → NaN Frontend Unfixed ▶
Datei: InvoicesView.tsx, types.ts
Risiko: NaN in KPI-Cards, falsche Summen
Backend liefert manchmal amountNet (englisch), manchmal amountNetto (deutsch). Frontend hat Fallback: inv.amountNet ?? inv.amountNetto. Wenn keines vorhanden → undefined → KPI-Berechnung zeigt NaN.
Fix: Normalisierung in api/client.ts: response.amountNet = response.amountNet ?? response.amountNetto ?? 0
B-017 High Bulk-Operationen: Kein Feedback bei Teil-Fehler Frontend Unfixed ▶
Datei: OrdersView, ReturnsView, ShippingView
Risiko: Stille Fehlschläge

Fix: Einzelergebnisse aus response.data.results auswerten und als Liste anzeigen: "8/10 erfolgreich, 2 fehlgeschlagen: [Details]".

S-001 Security JWT Token in URL-Query (SSE Streams) Backend Known BUG-SSE ▶

S-002 Security XSS via Product Titles aus eBay/Kaufland Backend Unfixed ▶

S-003 Security Kaufland Webhook ohne Signatur-Validierung Backend Unfixed ▶

S-004 Security Kunden-Email nicht validiert Backend Unfixed ▶

Fix: Einfache Email-Regex-Validierung in mapEbayOrder() und mapKauflandOrder().
