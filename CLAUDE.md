## Architektur (Kurzform)

- **Frontend:** React 18 + TypeScript + Vite + Tailwind → Firebase Hosting
- **Backend:** Node.js 20 + Express (CommonJS) → Cloud Run (europe-west3)
- **DB:** Firestore (Collection: `products_v2`, USE_PRODUCTS_V2=true)
- **KI:** Google Gemini API
- **Auth:** Firebase Authentication
- **Deployment:** `main` → GitHub Actions (Frontend) + Cloud Build (Backend)
- **Web/Worker-Split (seit 2026-06-29):** Dasselbe Backend-Image läuft als ZWEI Cloud-Run-Services. `product-hub-backend` (web, `RUN_BACKGROUND_JOBS=false`) bedient nur HTTP-Requests. `product-hub-worker` (`RUN_BACKGROUND_JOBS=true`, CPU always-on, min=max=1, ingress internal) fährt ALLE Runner + Safety-Net-Crons. Gate via `lib/process-role.js` in `index.js`. Zwei Build-Trigger auf `main` (web + `deploy-product-hub-worker-on-main`). **Neue Cron-/Runner-Jobs gehören in den `if (RUN_BACKGROUND_JOBS)`-Block in `index.js` — dann laufen sie automatisch nur auf dem Worker.** Details: `docs/runbooks/web-worker-split.md`.

## Feature-Flags (Backend ENV-Vars)

### Erfassung: Produktsuche statt Barcode-Vergleich (seit 2026-08-18)
Der Duplikat-Check der Erfassung verglich ausschliesslich Barcodes — `findProductByStrictIdentifier` (`lib/firestore.js`) prueft `identification.barcodes`, `details.identifiers.ean`, `.gtin` und `.sku`, sonst nichts. ### Versandetiketten: exaktes Rollenmaß + Drucken über AvyCloud (seit 2026-08-24, Betreiber-Anweisung)
Drei zusammenhängende Betriebsprobleme am Packtisch, gemeinsam behoben.

- **EXAKTES ROLLENMASS.** DHL + DPD → **103 × 164 mm**, Deutsche Post → **62 × 100 mm**. Vorher reichte `GET /api/orders/:orderId/label` das SendCloud-PDF (≈ A6, 105 × 148 mm) **unverändert** durch; der Druckertreiber skalierte selbst, mit Voreinstellungen die niemand kontrolliert. Neu: `lib/label-format.js` (EINZIGE Quelle des Zielmaßes) + `lib/label-pdf-resize.js` (pdf-lib, neue Seite in exakt der Rollengröße, Original proportional zentriert hineingelegt).
    - **ES WIRD NIE BESCHNITTEN.** Randlos füllen hieße überstehende Teile abschneiden — das kann der Barcode sein. Zwei weiße Streifen sind besser als eine unscannbare Sendung. `computePlacement()` wählt zwischen 0° und 90° das, was größer hineinpasst — das ersetzt jede Hoch-/Querformat-Heuristik und richtet ein quer geliefertes Etikett von selbst auf.
    - **PRÄFIX, NIEMALS `includes()`.** `'dp'` steckt in `'dpd'` — ein Teilstring-Test schickt jedes DPD-Paket auf die 62-mm-Briefrolle (das war der Vorfall 2026-07-11 „DP-Wahl erzeugte DPD-Label"). `optionCodePrefix()` schneidet am Doppelpunkt. Vorrang: `shippingOptionCode` (genau) vor `carrier` (grob).
    - **FAIL-OPEN.** Unbekannter Transporteur → `resolveLabelFormat` liefert `null` → **es wird nicht skaliert**, das Original geht raus. Unlesbares PDF → `resizeLabelPdfSafe` reicht das Original durch. Ein Etikett im Herstellermaß ist brauchbar; gar keines stoppt den Versand.
    - Antwort-Kopfzeilen `X-Label-Format` / `X-Label-Printer-Role` / `X-Label-Width-Mm` / `X-Label-Height-Mm` / `X-Label-Resized` / `X-Label-Scale`. `shipments.shippingOptionCode` wird jetzt additiv mitgeschrieben (Altsendungen fallen auf `carrier` zurück).
    - **WEISSRAUM WIRD FREIGESTELLT (seit 2026-08-31) — das war die Ursache des „winzigen" DP-Etiketts.** SendCloud liefert A6; beim Deutsche-Post-Maxibrief belegt der Inhalt davon **gemessen nur 34,5 × 70,1 mm = 15,5 %**. Wurde die GANZE Seite eingepasst, landete der Inhalt bei 59 % und der Frankier-Code bei ~7 mm. `lib/label-ink-box.js` bestimmt jetzt den bedruckten Bereich und `embedPage(page, boundingBox)` stellt ihn frei: **59 % → 133 %, Faktor 2,26**, Frankier-Code ~18 mm. **INHALT wird nie beschnitten, nur Weissraum** (2,5 mm Sicherheitsrand). DHL/DPD bleiben unangetastet — deren Etiketten füllen die A6-Seite bereits (Deckung > 92 % → kein Zuschnitt).
        - **Ohne Rasterer**, weil das Produktions-Image `node:20-slim` ist (kein Poppler/Ghostscript): der Kasten kommt aus den Zeichenbefehlen — Text über `getTextContent()`, Bilder und Pfade über die Operatorliste mit eigener Matrix-Verfolgung (`pdfjs-dist@3.11.174`, reines JS). **Gegen einen gerasterten Referenzwert geprüft: Abweichung < 1 mm.**
        - **Beschneidungspfade zählen NICHT als Inhalt.** Ein SendCloud-Etikett setzt als Erstes die ganze Seite als Clip — würde man den mitzählen, wäre der Kasten immer die volle Seite und das Freistellen wirkungslos. Ein Pfad zählt erst, wenn er auch gemalt wird.
        - **`width`/`height` aus `getTextContent()` sind LÄNGEN im Nutzerraum, keine Textraum-Größen.** Bei gedrehtem Text — und genau so zeichnet SendCloud das DP-Etikett — dürfen sie NICHT entlang x/y aufgetragen werden, sondern über die Richtungsvektoren der Matrix. Sonst wandert der Kasten hunderte Millimeter daneben (gemessen: y bis −299 mm).
        - **Fail-open in beide Richtungen:** Deckung > 92 % (nichts zu gewinnen) oder < 1,5 % (Erkennung hat wohl etwas übersehen) → ganze Seite. Gedrehte Quellseite (`/Rotate ≠ 0`) → kein Zuschnitt, weil pdf.js-Sichtraum und pdf-lib-Seitenraum dann auseinanderlaufen. Jeder Fehler → ganze Seite.
        - Notbremse `LABEL_CROP_WHITESPACE='off'`. Kopfzeilen `X-Label-Cropped`, `X-Label-Ink-Mm`.
    - **Restrisiko — Deutsche Post lag vor dem Freistellen bei 59 %.** Alle Etiketten kommen laut Firestore von `…/labels/label_printer/…`, und das ist bei SendCloud **A6 (105×148 mm)**. Auf die Paketrolle sind das 98 % (unkritisch), auf die 62×100er Briefrolle **59 %** — gemessen, im Test festgehalten. Ein Barcode hat eine Mindest-Modulbreite; darunter liest ihn der Handscanner im Verteilzentrum nicht mehr zuverlässig und die Sendung bleibt liegen. Deshalb warnt `resizeLabelPdfSafe` unter `SCALE_WARN_BELOW=0.75` im Log und meldet den Faktor als `X-Label-Scale`. **Muss an einem ECHTEN DP-Etikett gescannt geprüft werden** — geht das nicht, ist die 62-mm-Rolle das falsche Medium für SendCloud-DP-Etiketten (dann größere Rolle statt Beschnitt: beschneiden kann den Barcode köpfen).
    - **Transporteur-Werte in `shipments` sind gemischt geschrieben:** der SendCloud-Abgleich (`source:'sendcloud_sync'`) schreibt `"DP"` / `"DPD"` GROSS, `createParcel` schreibt `parcel.carrier.code` klein. `resolveLabelFormat` normalisiert deshalb vor dem Nachschlagen — Test vorhanden, nie entfernen.
    - `LABEL_EXACT_SIZE=''` (default an; **nur exakt `'off'`** schaltet ab — gleiche Strenge wie `AUTO_INVOICE`, ein Tippfehler darf das Druckbild nicht still ändern).
- **DRUCKEN LÄUFT ÜBER AVYCLOUD, NICHT ÜBER ANDROID.** Vorher ging jeder Druck über `navigator.share` → Androids Teilen-/Druckauswahl, und der Drucker war jedes Mal Handarbeit. `printToLabelPrinter()` in `api/client.ts` war **tote Verdrahtung** (null Aufrufer) und hätte nie funktionieren können: eine HTTPS-Seite darf kein `http://` im LAN aufrufen (gemischte Inhalte).
    - **Warum eine Warteschlange:** Cloud Run (europe-west3) erreicht eine private LAN-Adresse **prinzipiell nicht** — dieselbe Wand wie beim Foto-Agenten. Also legt AvyCloud den Auftrag ab (`print_jobs`) und `tools/print-agent/` im Büro holt ihn und druckt via CUPS (`lp -d … -o media=Custom.103x164mm`).

### Gemini-Infrastructure
- `GEMINI_PROMPT_CACHE=true` (default) — aktiviert Prompt-Caching via `backend/lib/prompt-cache.js`. 90 % Kosten-Ersparnis auf System-Prompts bei wiederholten Calls (Bulk-Ops, Multi-Turn-Chats). Min. 4096 Tokens für Cache-Eligibility, default TTL 60min.
- `ATOMIC_TOOLS_TIMEOUT_MS=15000` (default) — Per-Executor-Timeout für atomic-tools Library (`lookup_gtin`, `search_ebay_catalog`, `get_required_aspects`, `verify_brand`, `search_amazon_product`, `search_manufacturer_site`, `fetch_url_content`).

### Observability (Sprint 1 Tag 1+2)
- `EXTERNAL_API_TRACKER_SAMPLE_RATE=1.0` (default, 0..1) — Sample-Rate für `external_api_calls`-Firestore-Writes (`backend/lib/external-api-tracker.js`). Tracker erfasst pro Call: service (`serpapi`, `brightdata`, …), endpoint, success, latencyMs, errorCode — fire-and-forget, NIE blocking. Default 1.0 sammelt jeden Call; nach Baseline-Daten (~2 Wochen) auf `0.1` drosseln, um Firestore-Write-Volumen zu reduzieren. Genutzt von `/api/health/identify` (Aggregat-Stats für Operator-Dashboard) — Antwort auf „brauchen wir BrightData noch?" mit Daten statt Meinungen.

### LLM-Quality-Parity (Phase F.3 + Telemetry)
Schema-Validation und Telemetrie-Sampling für die LLM-Quality-Parity-Charta (`docs/standards/llm-quality-parity.md`).
- `LLM_SCHEMA_STRICT=false` (default) — Phase F.3 Stufe 1 (safeParse-warn). Validiert LLM-Responses gegen Zod-Schemas und loggt nur Warnings bei Fehlern. Setze `true` für Stufe-2-strict-throw NUR nach min. 7d safeparse-Beobachtung pro Scope ohne neue Schema-Violations. ENV-Var. Sub-Flag `LLM_SCHEMA_VALIDATE_RATE` steuert das Sampling.
- `LLM_SCHEMA_VALIDATE_RATE=1.0` (default) — Sample-Rate für Stufe-1-Logging (Float 0..1). `1.0` validiert jeden Call, `0.1` nur 10 % der Calls. Volume-Drossel für hot scopes.
- `LLM_TELEMETRY_SAMPLE=0.1` (default) — Sample-Rate für `llm_call_telemetry`-Schreibungen in Firestore (Float 0..1). Auto-Downgrade auf 0.1 nach 24h wenn ENV-Wert >0.5 (Cost-Guard). Kann via Firestore-Doc `system/llm-telemetry-state` runtime-überschrieben werden — ENV gewinnt bei Konflikt. Siehe `docs/standards/llm-quality-parity.md` §Telemetrie.
- `TENANT_ID=avycloud` (default, Scripts-only) — Default-Tenant für CLI-Scripts ohne explizites `--tenant`-Flag. Operator muss explizit `--tenant trendocean` setzen oder `TENANT_ID=trendocean` exportieren für Multi-Tenant-Runs. NIE für Production-Backend-Code lesen; nur Scripts.

## Chat-Assistant-Architektur (seit 2026-04-22)

### 3 Pipelines in Kaskade
1. **V3** (`backend/services/product-chat-v3.js`, flag `CHAT_V3`): Gemini 3.1 Pro Customtools mit `googleSearch + urlContext + 7 atomic-tools + update_datasheet` in einem Request. Thinking Mode high, Thoughts-Streaming, Cross-Reference + Confidence-Scoring post-generation. **Default ON (Code-Default: true).**
2. **V2** (`backend/services/product-chat-v2.js`): Google Search Grounding + custom function declarations. Mit `CHAT_V2_ENHANCED=true` zusätzlich urlContext, Temperature 1.0, Thinking. Default-Pipeline wenn V3 aus.
3. **Legacy** (`backend/services/product-chat.js`): BrightData/SerpAPI external tools. Mit `CHAT_LEGACY_ENHANCED=true` Amazon-Routing, forceEvidencePass für alle Intents. Fallback-only.

Routing: `req.body.pipeline` kann `'v3'|'v2'|'legacy'|'auto'` (default) setzen. Bei Error in einer Pipeline automatischer Fallback zur nächsten.
